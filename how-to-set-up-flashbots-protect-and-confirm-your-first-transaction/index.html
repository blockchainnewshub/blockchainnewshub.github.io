How to set up Flashbots Protect and confirm your first transaction

Flashbots Protect setup to confirmed transaction: add the Mainnet RPC, sign in MetaMask, track the private transaction on its status page, then confirm its block on Etherscan.

By Crypto Docket NewsroomNov 23, 2026 · 16:06 UTC#675a8e4 min read

Flashbots Protect works by routing a newly signed Ethereum Mainnet transaction through a private RPC, then letting you track it on the Protect status page and confirm its block on an explorer. Switching RPCs only affects transactions you sign afterwards; anything already sent through the public RPC remains public and may hold up the next transaction.

Before setup, make sure the wallet has ETH for gas and no pending transactions. Use Flashbots at this step to route new transactions through its Protect service. That changes the route for transactions signed after you switch, while the regular public RPC remains an alternative for transactions you choose to send publicly.

Clear public pending transactions before switching

A public transaction can block a later private one because Ethereum processes transactions from the same wallet in nonce order. Switching the wallet to Protect does not move, hide, or cancel a transaction already sent to the public mempool.

Open MetaMask and look for pending activity before adding the new route. Let each public transaction confirm, or resolve it using the wallet controls associated with the RPC that sent it. Then verify that no transaction is still pending. This gives the first protected transaction the next available nonce without an earlier public transaction in front of it.

Say you submitted a swap on the default RPC and it is still pending. A new swap signed through Protect uses a later nonce, so it cannot be processed first. The first swap remains visible to the public mempool, and the protected swap waits behind it until the earlier transaction clears. Switching networks alone does not solve that queue.

Add the Mainnet Protect RPC and choose a mode

Adding the Protect RPC as a custom network gives MetaMask a private route for transactions signed while that network is selected. For Mainnet, enter the RPC endpoint rpc.flashbots.net and chain ID 1 when creating the custom network, then save it and switch to it.

Fast mode is an optional choice for quicker inclusion: it shares transactions with all registered builders. The mode changes who receives the transaction within the builder system; it does not change the need to check the transaction's status and final inclusion.

Before signing, confirm that MetaMask shows the Protect network and that the transaction is intended for Mainnet. Have ETH available to cover gas. With the wallet clear of pending public transactions and the new RPC selected, prepare the swap or other transaction as usual and review its details.

Sign normally, then track the private transaction on Protect

After you sign through the selected Protect RPC, the transaction is private from the public mempool, so a pending transaction may not appear on a public explorer. Use the Protect status page to look up its hash and follow its status while it is pending.

Copy the transaction hash from MetaMask's activity details and search for it on the Protect status page. This is the right place to check whether the private transaction is still pending or has progressed. A missing result on Etherscan while it is pending does not by itself mean the transaction failed; the private route makes the Protect status page the relevant tracker at this stage.

Once the transaction is included in a block, look up the same hash on Etherscan. The task is complete when the explorer shows the transaction in a block. That confirmation is the visible evidence that the transaction was included on-chain, rather than merely signed or still waiting for a builder.

Use the status and transaction details to diagnose delays

A delayed private transaction calls for checking its Protect status and the wallet's nonce queue before resubmitting. If the status page still shows it pending, give it time and avoid signing another transaction that depends on the same sequence. If a prior public transaction remains pending, resolve that first; the next private nonce cannot pass it.

A swap that would revert is dropped rather than included. Re-quote the trade to refresh its expected output, then review slippage. Widen slippage only as far as the trade's price movement reasonably requires; excessive tolerance can let the swap execute at a worse rate than intended. Sign the revised transaction through the selected Protect RPC and track its new hash.

For the next transaction, the useful signals are simple: MetaMask is on the Protect network, no older public nonce is pending, the status page recognizes the signed hash, and Etherscan eventually shows its block. Those checks distinguish a routing or queue delay from a transaction that has completed.
