How to check a private Ethereum transaction: confirm inclusion

How to check if a private Ethereum transaction was included: search its hash for a receipt, then read the block number and execution status.

By Crypto Docket NewsroomNov 24, 2026 · 01:06 UTC#7020265 min read

A private Ethereum transaction is included when its transaction hash returns a receipt with a block number. Private submission can keep it out of public pending-transaction views, but inclusion is recorded on-chain. The receipt’s status tells you whether execution succeeded or failed.

Start with a transaction you sent from your wallet. Open its activity or confirmation screen and copy the transaction hash. This hash is the lookup key; a wallet’s “pending” label or a missing result in a public pending list does not settle whether the transaction has been mined.

For a transaction sent through Flashbots Protect, use the same hash-based check. Our article on Flashbots Protect transaction setup covers how to set it up and confirm a transaction. Flashbots Protect is the submission context; the receipt is what tells you about inclusion.

How do you check whether the transaction was included?

Search the hash on an Ethereum block explorer, or query an Ethereum RPC with eth_getTransactionReceipt. Make sure the explorer or RPC is on Ethereum mainnet if that is where you sent the transaction. If you used another network, select that network instead: the hash alone does not tell an explorer which network to search.

On an explorer, paste the full hash into its search field and open the matching transaction result. With an RPC, request eth_getTransactionReceipt using the hash. The method returns a receipt for a mined transaction, or null when that RPC has no receipt available for it.

A receipt containing a block number confirms that the transaction was included in that block. Read the receipt’s status separately to see whether execution succeeded or failed. Those are two different outcomes: a transaction can be included even when its execution fails. The block number answers the inclusion question; the status answers what happened during execution.

That check works because private submission and on-chain inclusion are different stages. Before inclusion, a private transaction may not appear in the public pending lists people often use to track activity. Once mined, its transaction contents are public on-chain. So a public pending view can miss the wait, while a receipt can confirm the result after inclusion.

There is also a privacy trade-off to understand. Before inclusion, the private RPC can associate distinctive information with the submission, including the sender’s IP address, the sender’s address and the timing. After inclusion, the transaction contents are public. A private route changes who can see the transaction while it is waiting; it does not make an included transaction permanently private.

Say your wallet shows a pending transaction, but searching its hash on Etherscan returns no result. That result alone does not establish that the transaction failed or was dropped: the public pending list may not show a private submission. Query the RPC for the same network or retry the lookup later. If you change the case slightly and sent the transaction on a different Ethereum network, the hash stays the lookup key, but you must search that network’s explorer or RPC. The receipt and status still answer the same questions once the correct network returns a receipt.

What if there is no receipt, or the status shows failure?

A missing receipt means that the RPC you asked has not found a mined receipt for that hash. Confirm that you copied the full hash and selected the network where the transaction was sent, then try the same network’s RPC again later. A null result is a time-specific lookup result, not a receipt with a block number.

Once a receipt appears, use its two relevant fields for two separate checks. The block number confirms inclusion. The status indicates whether the transaction’s execution succeeded or failed. If the status indicates failure, the transaction was still included; the failure describes execution, not whether a block contains it.

Watch for the change from no receipt to a receipt with a block number. That is the signal that resolves inclusion. Then read status to understand execution. Until then, a private transaction’s absence from a public pending view is consistent with private submission, so use the hash and the correct network as your reference.

Why is my private Ethereum transaction not showing on Etherscan?

Private pending transactions may not appear in public pending-transaction views. Search the transaction hash on the correct network, and query an Ethereum RPC for a receipt. A receipt with a block number confirms inclusion even when the public pending view did not show the transaction while it was waiting.

How do I find my Ethereum transaction hash?

Open the wallet’s transaction activity or confirmation screen and copy the hash for the transaction you want to check. Use the complete hash with an explorer or RPC on the network where you sent it. Then read the receipt’s block number and status.

  • Copy the transaction hash from wallet activity.
  • Search it on the correct network’s explorer or query an Ethereum RPC with eth_getTransactionReceipt.
  • A receipt with a block number confirms inclusion; status indicates execution success or failure.
  • If no receipt is available, confirm the hash and network, then retry later.
