Why a Cross-Chain Bridge Can Wait on a Public RPC

A bridge can be ready while a public RPC is not; see why endpoint lag stalls cross-chain updates, how it differs from a failed transfer, and what to check next.

By Crypto Docket NewsroomOct 17, 2026 · 08:20 UTC#7a9e345 min read

A cross-chain bridge can show a transfer as pending because the public RPC it relies on has not delivered a usable update, even when the source transaction is already onchain. Compared with a failed transaction, this is often a delay in reading or relaying information; compared with a private or self-operated endpoint, a shared public RPC can be easier to access but less predictable under load. The distinction matters: waiting for an update is different from sending the transfer again, which could create a second transaction.

A bridge needs to learn that an event happened on one chain before it can arrange or confirm the next step on another. It may do that through its own infrastructure, through a relayer, or through a front end that reads chain data from an RPC provider. RPC, short for remote procedure call, is the interface software uses to ask a node for information or to submit a transaction. It is not the blockchain itself. If that interface is slow, limited, or behind the chain’s latest state, the bridge’s view can lag the network.

For readers comparing the user steps across services, the Across Bridge’s five steps for moving assets offer a concrete walkthrough. The broader point applies beyond any one bridge: several separate systems have to agree on what happened before a transfer looks complete.

Why does a public RPC make a bridge wait?

A bridge waits when the data it needs has not reached the component responsible for checking or acting on it. A public RPC endpoint serves many users and applications, and providers may apply rate limits or return errors when demand is high. It can also respond more slowly than another endpoint or provide a view that has not yet caught up with recent blocks. The bridge may then retry its request, wait for another check, or continue only after it can verify the required event.

That creates a visible gap between the chain and the interface. A wallet may show a confirmed source transaction while the bridge page still says pending, because those displays can rely on different data paths and update schedules. A bridge’s relayer may also be waiting for its own checks, which can include the chain’s confirmation or finality rules. An RPC delay is one possible cause of a pause, but it does not explain every pending transfer.

The practical trade-off is availability versus control. A shared public endpoint is convenient and requires no infrastructure from the user. A provider’s dedicated service or an operator’s own node can offer more control over access and performance, but someone must configure, pay for, and maintain it. Neither option changes the bridge’s security rules or makes the destination action instantaneous; it changes how reliably software can query or submit data.

How can you tell an RPC delay from a failed transfer?

Start with the source transaction’s status on the source chain, then compare it with the bridge’s displayed status. If the transaction is still pending or failed in the wallet or chain explorer, the issue is upstream of the bridge’s later steps. If it is confirmed onchain but the bridge has not advanced, the transaction may be waiting for the bridge’s checks, a relayer, or a data update. A mismatch is a clue to investigate, not proof that the public RPC is at fault.

Check the transaction hash and the exact network before taking action. A correct hash lets you look up the original transaction independently of the bridge page. Read the bridge’s status and any stated waiting period or support guidance; confirmation requirements and completion steps vary by bridge and route. Avoid submitting a second transfer simply because one screen has not refreshed. If the original transaction succeeded, a duplicate can move additional funds rather than resolve the first transfer.

Useful checks are:

  • Confirm the source transaction’s status and destination details on the correct chain.
  • Refresh the bridge page or reconnect the wallet, then compare the status again.
  • Check whether the bridge reports a relayer or destination step still in progress.
  • Keep the transaction hash and use the bridge’s official support route if its stated process appears stuck.

These checks help separate a display that has not updated from a transaction that did not succeed. They do not establish that an endpoint is healthy, and a generic RPC status page may not reflect the endpoint actually used by the bridge or wallet.

What should you do while the bridge is pending?

Wait for the bridge’s stated process to advance before repeating a transfer, and use the source transaction hash to track what already happened. If the source transaction is confirmed and the bridge remains pending beyond its own guidance, collect the hash, route, and status message for support. A wallet’s option to change its RPC can help diagnose whether that wallet is reading stale data, but it may not change the bridge’s backend or relayer, which can use separate infrastructure.

For most readers, the better default is to verify the transaction and follow the bridge’s own status instructions rather than switch endpoints or resubmit immediately. An alternate RPC can provide a useful second view, but different endpoints can disagree temporarily, and changing one does not reverse or speed up an already confirmed transaction. The next signals to watch are whether the source transaction is confirmed, whether the bridge recognizes it, and whether the destination step moves from pending to complete.
